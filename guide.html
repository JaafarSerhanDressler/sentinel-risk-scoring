Overview

Sentinel is the Participant Risk Response App. A daily ML pipeline (“Fabric”) scores every participant across four programmes; the app turns those scores into actionable alerts and records the response — all on synthetic data in the non-production environment.

Score & alert

Three risk types per participant — dangerous behaviour, medication refusal, medication non-compliance — each with probability, severity and band, driving one open alert per type.

Route & escalate

Emergencies notify every level at once; warnings follow the programme chain with acknowledge and action clocks. Hospitalisation puts alerts on hold.

Record & audit

Staff record actions (seven categories) against each alert; an append-only audit trail and action log flow back to Fabric for the data team.

Architecture

Source systems feed the Fabric pipeline; the app ingests only completed daily runs, serves the response workflow, and writes an action log back. Every external system sits behind an adapter with a fake now and a real one later — switching is configuration only.

ASP.NET Core API

Hosts the PWA on the same origin and exposes /api/*. Mocks the Fabric read, holds participants/programmes/runs and the audit log.

Adapters (fake → real)

Fabric, Dayforce, Entra, notifications and email each sit behind an interface; the real implementation drops in later without app changes.

The app reads only completed runs (by run status). A failed validation rejects the run and keeps the previous one live; the “risk as of” date (Credible / ChartMeds) is shown throughout.

Risk types & bands

Each participant is scored for three risk types, every one with a probability (0–1), a severity (1–5) and a band. An overall danger severity (1–5) and an overall band drive the gauge.

Dangerous behaviour

From behaviour events in the last 90 days (category, severity, subject/victim, dropdown or NLP source).

Medication refusal

Refusal counts & streaks; a long streak (150+ days) is a flagged case.

Medication non-compliance

Missed doses, declining adherence, restart flags (clozapine, exelon, lamictal). PRN doses are excluded.

High
High band
Top tier — proactive response; emergencies escalate immediately.
Moderate
Moderate band

Low band
Routine monitoring; eligible to be marked ready to close.
Explainability & reliability: every score lists the behaviour & medication events behind it, and carries a data-reliability flag (sufficient / not enough information) with detail such as “Form 1224 Overdue (>90d)”.

Alerts & escalation

One open alert per participant per risk type. Alerts are emergency or warning and move through a defined set of states.

Alert states

Open · Acknowledged · In progress · Ready to close · On hold · Closed. Transitions are append-only history; frontline staff never close.

Escalation

Emergencies notify every level at once. Warnings follow the programme chain with two clocks — acknowledge, then first documented action — resolving roles to people through the org structure. Holds stop all timers; hospitalisation holds the alert.

Screen-by-screen

Mobile-first care surfaces with a bottom nav + FAB; the Fabric console expands on desktop.

1 · Sign in

Entra sign-in with role by email (admin / supervisor / clinical / frontline); a demo account for instant exploration.

2 · Dashboard

Open alerts, emergencies, high band and participant KPIs with the “risk as of” date, a band distribution donut, daily scoring volume, priority alerts and a live activity feed.

3 · Participants

Searchable, risk-sorted list with emergency and band filters; each row shows programme, case manager (or unassigned) and alert state.

4 · Participant detail

Header with programme, keyworker, site, alert class & state and reliability; gauge, the three risk types, 12-week trajectory, behaviour & medication events and the recommended response.

5 · Programmes

BH RES, ICMS, SH and SH SUBONLY with participants, open alerts, emergencies and average score; drill into a programme’s people.

6 · Run assessment

Pick a participant + data sources → stepped ML Fabric overlay → animated result with gauge, risk types and 90-day signal counts.

7 · Fabric console

Model KPIs, performance & drift, the daily run log (completed / failed / late), data-source health and recent re-scores, with a Power BI export.

8 · Audit logs

Severity-filterable, append-only event stream with actor, action, category, timestamp and correlation id.

Use cases

What staff accomplish with Sentinel.

  1. Emergency response. An emergency alert surfaces a participant immediately and notifies every escalation level at once.
  2. Medication refusal streak. A 150+ day refusal streak is flagged for medication follow-up before it becomes non-compliance.
  3. Insufficient data. Participants flagged not enough information (e.g. Form 1224 overdue) prompt the overdue assessment.
  4. Hospitalisation hold. A hospitalised participant’s alerts go on hold and all timers stop.
  5. Ready to close. When risk drops below the alert level, the alert is marked ready to close and the outcome recorded.
  6. Fabric governance. Admins watch run status, drift and source health, and trace any score through the audit log.

Install as an app (PWA)

Sentinel is a standalone, installable progressive web app with an offline-ready service worker and shared-device sign-in.

On mobile

Open the site in the browser, then Share → Add to Home Screen (iOS) or the Install app prompt (Android). It launches full-screen.

On desktop

Click the Install icon in the address bar, or use the in-app Install App button that appears when installation is available.

Run locally

The API hosts the Blazor PWA on the same origin, so a single command runs everything.

  1. Prerequisite. Install the .NET 10 SDK.
  2. Build. dotnet build RiskScoring.slnx
  3. Run. dotnet run --project src/RiskScoring.Api --launch-profile Sentinel
  4. Open. Browse to http://localhost:5080 and sign in (role by email: admin / sup / clin, otherwise frontline).
All participants, scores, events and runs are synthetic and generated for demonstration. No real participant data is present.
